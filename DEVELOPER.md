## GitHub Spec Kit

<!-- cspell:ignore speckit taskstoissues -->

[GitHub Spec Kit](https://github.com/github/spec-kit) (MIT) brings **spec-driven development (SDD)** to AI coding
assistants: you describe *what* a feature should do and *why*, agree a technical plan, break it into tasks, and only
then let the assistant write code against those files. Every step leaves a Markdown file you can review, so the
intent behind a change stays in the repository next to the code.

This guide was checked against Spec Kit **v1.2.1** (released 2026-10-16) on 2026-10-18. Spec Kit changes quickly;
if a command or flag below doesn't match, the [Spec Kit documentation](https://github.github.io/spec-kit/) for your
version wins.

### When to use it for a PPTB tool

| Work | Use |
| --- | --- |
| A new tool, or a feature that adds behavior users see (a new setting, card, dialog, generated file) | Spec Kit |
| A change with unclear requirements, or several people who must agree first | Spec Kit, with `/speckit-clarify` |
| Restructuring code without changing behavior | The `aidevme-pptb-tool-refactoring` skill |
| A small, obvious fix (a typo, a wrong label, a one-line bug) | Ask the assistant directly |
| Diagnosing a bug with an unknown cause | Optional: Spec Kit's `bug` extension (`specify extension add bug`) |

Spec Kit adds files and review steps, so it pays off when a misunderstanding would be expensive: anything that
writes to Dataverse or the user's files, changes generated output, or needs marketplace review.

### How it fits this repository

| Piece | Role |
| --- | --- |
| Spec Kit (`specify` CLI and the `speckit-*` skills it installs) | Writes the constitution, specs, plans and tasks, and runs the implementation and the convergence check |
| `aidevme-spec-kit` skill | Detects which phase a feature is in, runs the right `/speckit-*` command, checks the result and stops for your review between phases |
| `aidevme-github` skill | Every commit, branch, issue and pull request; Spec Kit's own git extension isn't used |
| `pptb-tool-dev` skill | PPTB API, manifest and `pptb-validate` questions while you plan and implement |
| `intake-policy-review` skill | A marketplace policy check before you open the pull request |

The rule of thumb: **Spec Kit owns the documents, `aidevme-github` owns git and GitHub, and you approve every
phase.**

### What you need

- **Python 3.11 or later** and [**uv**](https://docs.astral.sh/uv/) (`winget install --id=astral-sh.uv -e` on
  Windows, `curl -LsSf https://astral.sh/uv/install.sh | sh` on macOS and Linux). Check with `uv --version`.
- **Claude Code** (this guide's assistant). Spec Kit supports others, such as GitHub Copilot (integration key
  `copilot`), but the commands and folders differ; see the
  [integrations reference](https://github.github.io/spec-kit/reference/integrations.html).
- The tool's usual prerequisites: Node.js and npm, and the PPTB desktop app for live testing.
- A clean working tree on a feature branch, so everything Spec Kit generates shows up in one reviewable diff.

### Choose where Spec Kit lives

A Spec Kit project is the folder that contains `.specify/`. It holds its own constitution, its own `specs/` folder
and its own feature numbering. This repository hosts several independent tools, so **initialize Spec Kit once per
tool**, in `tools/<tool-name>/`:

```text
PPTB-Tools/
├── .claude/skills/              # the repository's skills (generated by agent-src/sync/sync.ps1)
└── tools/
    └── <tool-name>/
        ├── .specify/            # this tool's Spec Kit project: constitution, templates, scripts
        ├── .claude/skills/      # speckit-* skills, installed by specify init for this tool
        ├── specs/
        │   └── 001-<feature>/   # spec.md, plan.md, tasks.md, … for one feature
        └── src/ …
```

Why per tool rather than at the repository root:

- **Each tool has its own rules.** The generator must match dataverse-gen's output byte for byte; another tool
  might write to Dataverse. A per-tool constitution states the rules that actually apply.
- **The skills sync leaves it alone.** `agent-src/sync/sync.ps1` deletes and recreates every folder in the root
  `.claude/skills/`, so `speckit-*` skills installed there would disappear on the next sync. Skills in
  `tools/<tool-name>/.claude/skills/` aren't touched.
- **Claude Code sees both sets of skills.** Started in `tools/<tool-name>`, it loads the skills in that folder and in
  every parent folder up to the repository root
  ([Claude Code skills documentation](https://code.claude.com/docs/en/skills)). Started at the root, it loads a
  tool's nested skills only after it first reads or edits a file in that tool.

The `aidevme-spec-kit` skill follows the same layout: it works in the nearest `.specify/`, and when you ask it to set
up Spec Kit it proposes the tool's folder, never the repository root.

### Install and initialize

1. **Install the CLI, pinned to a release** (once per machine):

   ```bash
   uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@v1.2.1
   specify version
   ```

   To move to another release later, rerun the command with the new tag and `--force` (it replaces the CLI only).

2. **Start from a reviewable baseline:** commit or stash your work and create a branch, for example
   `feature/<tool-name>-spec-kit` (`aidevme-github` can name and create it).

3. **Initialize the tool's folder.** From `tools/<tool-name>/`:

   ```powershell
   # Windows (PowerShell scripts)
   specify init --here --integration claude --integration-options="--no-model-invocation" --script ps
   ```

   ```bash
   # macOS / Linux (Bash scripts)
   specify init --here --integration claude --integration-options="--no-model-invocation" --script sh
   ```

   - `--integration claude` installs the commands as skills in `.claude/skills/speckit-*` (the old `--ai claude`
     flag no longer exists).
   - `--no-model-invocation` makes those skills run only when you, or the `aidevme-spec-kit` skill, type
     `/speckit-<command>`. Claude doesn't start a phase on its own, and their descriptions don't crowd its context.
   - The folder isn't empty, so `specify init` asks before merging into it. Confirm only on a clean baseline.
     `--force` skips that question; never use it on a folder that already has `.specify/`.

4. **Don't add the git or agent-context extensions.** `specify init` installs neither in v1.2.1:
   - **git** would create branches and commits itself; here `aidevme-github` does that. If
     `specify extension list` shows it enabled, run `specify extension disable git`.
   - **agent-context** writes a managed block into `CLAUDE.md` and `AGENTS.md`. In this repository `CLAUDE.md` is
     generated from `AGENTS.md`, so leave it out.

5. **Check the result** before committing:
   - `.specify/` exists with `memory/constitution.md`, `templates/`, `scripts/` and `init-options.json`;
   - `.claude/skills/speckit-constitution`, `-specify`, `-plan`, `-tasks`, `-implement` and `-converge` exist;
   - `git status` shows no change to `AGENTS.md`, `CLAUDE.md` or anything outside the tool's folder.

6. **Commit the setup** through `aidevme-github` ("commit my changes"), then restart Claude Code in
   `tools/<tool-name>` so it picks up the new skills.

### The workflow

**One constitution per tool, then one feature folder per change:** constitution → specify → clarify → plan → tasks →
analyze → implement → converge. Run each command in Claude Code, started in `tools/<tool-name>`, and review its file
before the next one.

| Step | Command | Writes | What to check for a PPTB tool |
| --- | --- | --- | --- |
| 1. Principles (once per tool) | `/speckit-constitution` | `.specify/memory/constitution.md` | The marketplace rules and the tool's own invariants are there, each one checkable in a pull request |
| 2. Spec | `/speckit-specify <what and why>` | `specs/NNN-<slug>/spec.md` | What the user sees and why, user scenarios, testable acceptance criteria, and what's out of scope; no technology choices yet |
| 3. Clarify | `/speckit-clarify` | updates `spec.md` | No `[NEEDS CLARIFICATION]` marker left; what the feature changes in Dataverse or on disk is explicit |
| 4. Plan | `/speckit-plan <technical context>` | `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md` | Uses the tool's existing structure (React, Fluent UI v9, the `src/` folders), documented PPTB APIs only, and keeps the single IIFE build |
| 5. Checklist (optional) | `/speckit-checklist` | `checklists/*.md` | "Unit tests for the requirements": the spec is complete before work is split up |
| 6. Tasks | `/speckit-tasks` | `tasks.md` | Small, ordered tasks, each traced to a requirement, including tests, docs and the live PPTB check |
| 7. Analyze | `/speckit-analyze` | report only | No requirement without a task, no task without a requirement |
| 8. Implement | `/speckit-implement` | code, tests, docs; ticks tasks | Run one task (or a small group) at a time, with `npm run build` and `npm test` after each |
| 9. Converge | `/speckit-converge` | appends tasks if gaps remain | Repeat implement and converge until it reports **Converged** |

**Review gates.** Approve the constitution before the first spec, the spec before the plan, the plan before the
tasks, and the tasks before any code. "Do the whole thing" with `aidevme-spec-kit` still stops at each of these.

**Commits.** After each task passes its checks, ask `aidevme-github` to commit it; the message names the task
(for example `feat(<tool-name>): add the zip builder (T003)`). Push and open the pull request only after converge
reports Converged and you've tested in PPTB.

### Writing the constitution for a PPTB tool

Base it on rules that are already true for the repository (`AGENTS.md`, the tool's README, the
[marketplace](https://docs.powerplatformtoolbox.com/policies/marketplace) and
[AI-assisted development](https://docs.powerplatformtoolbox.com/policies/ai-assisted-development) policies), not on
wishes. Keep every principle short enough to check against a pull request. A starting point:

```text
/speckit-constitution Principles for this Power Platform ToolBox tool:
1. Changes to Dataverse or the user's files are previewed, confirmed with the target and scope named, and listed in
   the README's "What this tool changes" section. Nothing destructive runs on load.
2. Only documented toolboxAPI, dataverseAPI and powerplatformAPI calls; every external domain is declared in
   cspExceptions.
3. React + TypeScript (strict) + Fluent UI v9; colors from theme tokens, so light and dark themes both work.
4. The build stays a single IIFE bundle (vite.config.ts): no code splitting or ESM output.
5. New logic has vitest tests; npm run build, npm test and npm run validate pass before a task is done.
6. Every feature is tested live in PPTB, in light and dark themes and on its error paths, and the result is recorded
   in docs/pptb-tools/<tool-name>/contributing/testing.md.
7. Docs, README and TSDoc change in the same task as the behavior they describe.
```

Add the tool's own invariants. For the Dataverse Early-Bound TypeScript Generator, for example: "Generated output
matches dataverse-gen byte for byte, apart from the deviations listed in the README; `test/reference/` and
`test/fixtures/` stay in LF line endings." Change the constitution later only on purpose, with a dated line saying
what changed and why.

### Example: a feature end to end

A feature like the generator's **Generate templates** setting (a switch that stops Generate writing dataverse-gen's
EJS templates) would go like this, with Claude Code started in `tools/dataverse-early-bound-typescript-generator`:

1. **Spec:**

   ```text
   /speckit-specify Add a "Generate templates" setting. Users who maintain their own EJS templates need Generate to
   stop overwriting the copies in the project's templateRoot. On by default, so nothing changes for existing users.
   When off, Preview doesn't list the templates and Generate doesn't write them; existing copies stay on disk.
   ```

2. **Clarify:** answer the questions, for example "Is the setting per project or for all projects?" and "Where in
   the Settings panel does it appear?".
3. **Plan:**

   ```text
   /speckit-plan Store it as generateTemplates in the tool config (config/index.ts, the bundled JSON and its schema),
   default true. Show it as a Switch with an InfoLabel in its own card on the Settings panel's Generate & files tab.
   Leave the templates out of the write plan in usePreviewGenerate when it's off. Tests in vitest.
   ```

4. **Tasks and analyze:** expect tasks for the config key, the draft reset, the Generate hook, the Settings card,
   the tests, every docs page that says templates are written on each Generate, and the live PPTB check.
5. **Implement**, one task at a time, committing each through `aidevme-github`.
6. **Converge**, test in PPTB in both themes, run `intake-policy-review` if the change touches what the tool writes,
   then push and open the pull request. The pull request body links `spec.md`, `plan.md` and `tasks.md`.

### Using the aidevme-spec-kit skill

You can run the `/speckit-*` commands yourself, or let the `aidevme-spec-kit` skill drive them. It checks which
phase the current feature is in (no constitution yet, a spec without a plan, open tasks, and so on), says so, runs the
matching command, checks the resulting file and stops for your approval. It never commits; it hands commits, issues
and pull requests to `aidevme-github`. Example prompts:

- "Spec this feature: export the generated files as a zip."
- "Where is the zip export feature? Continue with the next phase."
- "Implement the next task."
- "Does the code still match the spec?"

For a Power Platform tool, its `power-platform` and `typescript-web` constitution profiles are a useful checklist
when you write the principles above.

### Keeping specs over time

Spec Kit doesn't decide what happens to a feature's files once it ships
([spec persistence models](https://github.github.io/spec-kit/concepts/spec-persistence.html)). Pick one rule per tool
and write it into the constitution:

- **Historical record:** each `specs/NNN-<slug>/` folder is frozen when the feature merges; later changes get a new
  feature folder. Simple, and the default here.
- **Living spec:** `spec.md` is kept up to date as the contract, and plans and tasks are regenerated from it.

Either way, commit the feature folder in the same pull request as the code.

### Customizing and upgrading

- **Customize** without editing Spec Kit's files: put a one-off template change in `.specify/templates/overrides/`,
  or install a reviewed preset (`specify preset add <id>`). Overrides win over presets, presets over extensions,
  extensions over the core templates. Don't edit `.specify/templates/`, `.specify/scripts/` or the `speckit-*`
  skills directly.
- **Upgrade:** commit first, reinstall the CLI at the new tag (`uv tool install specify-cli --force --from
  git+https://github.com/github/spec-kit.git@<tag>`), then run `specify integration upgrade claude` in each tool's
  folder. It stops if managed files were edited locally; check the diff before rerunning with `--force`. The
  constitution and your specs are kept. Installing or removing a preset turns `--no-model-invocation` off for the
  skills that preset overrides: run `specify integration upgrade claude --force` again afterwards.

### Troubleshooting

| Problem | Fix |
| --- | --- |
| `/speckit-*` commands don't appear after `specify init` | Restart Claude Code in `tools/<tool-name>`; new skills aren't picked up mid-session. Check that `.claude/skills/speckit-*` exists in the tool's folder |
| Claude never runs a Spec Kit phase by itself | Expected with `--no-model-invocation`: type the command, or ask `aidevme-spec-kit` |
| `specify: command not found` after installing | Open a new terminal so the uv tools folder is on `PATH`, then `specify version` |
| `--ai` flag rejected | Use `--integration claude` (renamed) |
| A feature landed in the wrong `specs/` folder | Start Claude Code in the tool's folder; Spec Kit uses the nearest `.specify/`. From the repository root, set `SPECIFY_INIT_DIR=tools/<tool-name>` before starting the assistant |
| `/speckit-taskstoissues` warns that it's deprecated | Create issues through `aidevme-github` instead |

## AI Agent Skills

Power Platform ToolBox publishes [pptb-agent-skills](https://github.com/PowerPlatformToolBox/pptb-agent-skills), a
set of skills that help AI coding assistants build, review and verify PPTB tools. They use the open `SKILL.md`
format, so Claude Code (and Cowork), GitHub Copilot and OpenAI Codex all read the same files. The skills are based
on the PPTB documentation, the marketplace policies and the `generator-pptb` scaffolding tool.

Source: [AI Agent Skills](https://docs.powerplatformtoolbox.com/tool-development/ai-agent-skills) in the PPTB
documentation. Check it for updates; the skills and the PPTB APIs they describe change over time.

### The skills

| Skill | Install as | What it does |
| --- | --- | --- |
| [`tool-dev`](https://github.com/PowerPlatformToolBox/pptb-agent-skills/tree/main/tool-dev) | `pptb-tool-dev` | Scaffolds, fixes, debugs, validates and publishes PPTB tools. |
| [`intake-policy-review`](https://github.com/PowerPlatformToolBox/pptb-agent-skills/tree/main/intake-policy-review) | `intake-policy-review` | Reviews a tool against the Marketplace Policy and the AI-Assisted Development Policy, and gives a readiness verdict. |
| [`tool-verification`](https://github.com/PowerPlatformToolBox/pptb-agent-skills/tree/main/tool-verification) | `tool-verification` | Checks a tool repository against the current Verified badge criteria. |

What each one covers:

- **`tool-dev`**:
  - scaffolding with `yo pptb`;
  - fixing `package.json` and `pptb.config.json` until `pptb-validate` passes (here: `npm run validate`);
  - letting other PPTB tools launch a tool (`launchTool`, `getLaunchContext`, `returnData`);
  - exposing a tool to agents through MCP (the `agents` block and `invokeHeadless`).
- **`intake-policy-review`**:
  - metadata;
  - read/write safety and the required "What this tool changes" README section;
  - API usage;
  - privacy and network behaviour;
  - screenshots;
  - testing;
  - a dependency audit.
- **`tool-verification`**:
  - Checks every required and optional maturity criterion.
  - Produces a criterion-by-criterion evidence table, notes on missing evidence, and a "Reviewer response" list
    for the verification form.
  - Verdicts: *Ready to request verification*, *Needs reviewer judgment*, *Not ready* or *Incomplete assessment*.

### Prerequisites

- Node.js and npm.
- The PPTB desktop app, for the debug loop (Debug → Browse). Scaffolding and validation don't need it.
- Claude Code or Cowork, GitHub Copilot, or OpenAI Codex, with skills enabled.
- For the review skills: access to the tool's repository and the policies, plus dated evidence from the tool's
  owner for any marketplace metrics.

### Installing the skills in this repository

This repository uses Claude Code, so project skills go in `.claude/skills/` (alongside the existing ones). From
Bash or Git Bash, in the repository root:

```bash
git clone https://github.com/PowerPlatformToolBox/pptb-agent-skills.git ../pptb-agent-skills

cp -r ../pptb-agent-skills/tool-dev/ .claude/skills/pptb-tool-dev/
cp -r ../pptb-agent-skills/intake-policy-review/ .claude/skills/intake-policy-review/
cp -r ../pptb-agent-skills/tool-verification/ .claude/skills/tool-verification/
```

Copy each whole skill folder, including any `references/` folder inside it. Note that `tool-dev` is installed under
the name `pptb-tool-dev`.

For the other assistants, copy the same folders to:

| Assistant | Skills folder |
| --- | --- |
| Claude Code / Cowork | `<project>/.claude/skills/` |
| GitHub Copilot | `<repo>/.github/skills/` |
| OpenAI Codex | `<repo>/.agents/skills/` (create it first with `mkdir -p`) |

### Scope and limitations

- **Scaffolding:** `tool-dev` scaffolds only with `generator-pptb`. It doesn't use the older
  [sample-tools](https://github.com/PowerPlatformToolBox/sample-tools) repository.
- **Example repository:** `Power-Maverick/PPTB-Tools` is used only as an example of patterns, not as a template.
- **Approval:** the skills don't replace marketplace approval or human testing. They can't grant a Verified badge
  or a reviewer waiver.
- **Maturity:** `tool-dev` isn't tested end to end yet. Its agent-integration guidance may describe APIs newer than
  the PPTB version you have installed, so validate generated code. In this repo, that means `npm run build`,
  `npm test` and `npm run validate` in the tool's folder, then a test in PPTB.
