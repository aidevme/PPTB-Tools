# ADR-0002 — Canonical repository structure

## Context
The template must hold, in one repo: (a) the **agent layer** serving both Claude and Copilot from one
source, (b) the **project wiki** (knowledge base), (c) the inherited **product tier**, and (d) the
**ProjectTemplate blueprint** a new engagement is generated from. The Part-1 (Agent) source analysis
(`docs/review-logs/part1-agent-01-source-analysis.md` §6) recommends a structure merging the live-delivery source's wiki,
HINT's dual-tool sync + template governance, and a new core/project skill split. This ADR adopts it as
the canonical layout so every part's builder writes to agreed paths.

## Decision — the tree

```
NewTemplate/
├── AGENTS.md                      # single instruction SOURCE → generates the two below
├── CLAUDE.md                      # GENERATED (Claude) — do not hand-edit
├── .github/
│   ├── copilot-instructions.md    # GENERATED (Copilot) — do not hand-edit
│   └── skills/                    # GENERATED mirror (sync output)
├── .claude/
│   ├── settings.json              # permissions (CDX pattern)
│   └── skills/                    # GENERATED mirror (sync output)
│
├── agent-src/                     # CANONICAL agent SOURCE (edit here only)
│   ├── AGENTS.md.tmpl
│   ├── sync/  (sync.ps1 · skills-manifest.json · verify-parity.ps1)
│   └── skills/
│       ├── core/                  # reusable product skills — grouped: foundation dataverse
│       │                          #   server client pipelines delivery reference meta
│       └── project/               # engagement-specific skills (never synced upstream)
│
├── agent/                         # PROJECT-tier wiki (live-delivery-source hybrid, visible, committed)
│   ├── README.md index.md log.md schema.md
│   ├── raw/ _inbox/
│   ├── wiki/ (system topics sop reference decisions digests people)
│   └── work/ (analysis specs design build testing deliverables)
│
├── shared/                        # PRODUCT-tier inheritance (gitignored junction; guard fails fast if absent)
│
├── ProjectTemplate/               # the blueprint a new project is generated from
│   ├── Server/                    # C# plugins/services/model/tests (ADR-0004)
│   ├── Client/clientjs/           # TypeScript client + RuleEngine (ADR-0005)
│   ├── PCFControls/               # PCF control template (ADR-0006)
│   ├── Functions/                 # Azure Functions (off-Dataverse compute)
│   ├── Pipelines/                 # ADO YAML with marker blocks (ADR-0007)
│   ├── PipelinesHelpers/config/   # pipeline-defaults.json · solution-organizer.json (+ scripts/)
│   ├── ReferenceData/{Schema,Data}/
│   ├── Solutions/
│   └── InitializeProjectScript/   # token-replacement engine + HANDOVER-RUNBOOK.md
├── Project/                       # active generated customer repo (gitignored) — not shipped
│
├── docs/ (decisions review-logs onboarding)  ·  PLAN.md  ·  _meta/
```

## Rationale
- **One source, two tools.** `agent-src/` is edited; `.claude/` + `.github/` + `CLAUDE.md` +
  `copilot-instructions.md` are generated by `agent-src/sync/sync.ps1` and verified by
  `verify-parity.ps1` (drift = fail). Removes HINT's twin-mirror drift surface (analysis §4.1).
- **core vs project skills** are separate source trees (analysis §4.4) — reusable skills round-trip to
  `shared/`; project skills never do; the manifest records each skill's scope.
- **Wiki = live-delivery-source hybrid** (`agent/`, 4 layers, no numbering), visible (un-dotted) scaffolding.
- **ProjectTemplate = CDX project shape + HINT spine.** It is the blueprint; `Project/` is the generated
  instance and is gitignored (never shipped in the template).

## Consequences
- Builders write ONLY within their subtree: Server→`ProjectTemplate/Server`, Client→`.../Client`,
  PCF→`.../PCFControls`, Pipelines→`.../Pipelines`+`PipelinesHelpers`, Agent→`agent-src`+`agent`+`.claude`+`.github`.
- The sync script and parity check are themselves Part-1 deliverables.
- Per-part architecture ADRs: 0004 server · 0005 client · 0006 PCF · 0007 pipelines (to be written by each part).
