| 2026-08-21 | Meghan Reed | **Fixed `Comment -CommentFilePath`, which failed 100% of the time under Windows PowerShell 5.1** — i.e. under the skill's own documented invocation (`powershell -ExecutionPolicy Bypass -File ...`). `Get-Content -Raw` returns an **ETS-decorated** string under PS 5.1 (carrying `PSPath` / `PSDrive` / `PSProvider` note properties); the `@{ text = $commentHtml } \| ConvertTo-Json` that follows then serialized it as an **object** — `{"text":{"value":"...","PSPath":...}}`, ballooning a 2 KB file into a 3.7 MB body — and ADO rejected it with HTTP 400 *"You must provide a value for the text parameter."* Under **PowerShell 7** `Get-Content -Raw` returns a plain string and the identical code works, which is why the 2026-08-12 live verification passed and this went unnoticed. Now reads via `[System.IO.File]::ReadAllText()` on a `Resolve-Path`-resolved path, so the value is a plain .NET string on every host. **The other three `Get-Content -Raw` reads in this script were checked and deliberately left alone** — `-JsonPatchFilePath` (x2) and `-TestStepsFilePath` pass their strings straight to bytes or through `.Replace()`, never through `ConvertTo-Json`, so ETS decoration is inert there. No parameter or output contract change. Verified live against a Dataverse-backed Azure DevOps org: posted an HTML comment to a Bug, `format: html`, entities round-tripped intact. |
| 2026-08-18 | Meghan Reed | Bug Tags row: a project's `CLAUDE.md` may mandate a lifecycle tag (e.g. fix-in-TST-not-yet-PRD), which overrides the general "only tag when asked" rule; use the project's tag string exactly — near-miss variants fragment the query the tag exists to serve. Reverse-promoted from a project fork. |
| 2026-08-17 | Meghan Reed | **`Invoke-AdoRestMethod` moved out to `../../hso-shared-scripts/scripts/ADO-WebApi.ps1`; both local copies deleted.** This skill held **two** definitions of it — the full one in `Invoke-AdoWorkItemOperation.ps1` (85 lines, `-Method` + `-Body`) and an already-drifted GET-only fork in `Get-AdoProcessProfile.ps1` (60 lines). The fuller version is now the shared one and both scripts dot-source it; **164 lines of duplication removed and no call site changed**, since the name and signature are identical and the reduced copy's callers only ever issued GETs. Nothing about this skill's behaviour changes except that the promoted function picked up a fix on the way: it read the `Location` header *after* closing the response, which works under .NET Framework but returns null under .NET, so on **PowerShell 7** a sign-in redirect threw `Cannot index into a null array` rather than the actionable message naming the token cache. Verified live after the move — `Get` on a work item and a full `Get-AdoProcessProfile` run both behave as before. |
| 2026-08-12 | Meghan Reed | **`Comment` + `GetComments` operations.** The skill could create, update, link and add test steps, but had no way to post to a work item's Discussion — yet consumer conventions mandate comments at several points (test-execution outcomes per test case and on the Test task, spec-completion handoff with an @mention, spec-deviation notification on the Design task, blocking-bug references). Every caller was hand-rolling the REST call. `Comment` takes `-CommentText`/`-CommentFilePath` (prefer the file for HTML) and returns the new comment id; `GetComments` returns the thread (`id`/`createdBy`/`createdDate`/`modifiedDate`/`text`) so a re-run can check whether it already posted. **@mention support** is the load-bearing part: a bare `@Name` posts fine and notifies nobody, so `-MentionFromField` (plus `-MentionFromWorkItemId`, or explicit `-MentionIdentityId`/`-MentionDisplayName`) resolves the identity from a work item field and builds the required `data-vss-mention` anchor — reading from work item payloads that already carry `{id, displayName}`, so **no PAT scope beyond Work Items (Read & Write)** is needed; empty field or GUID-less string fails loudly rather than posting a silent no-op. Both routes pin `api-version=7.1-preview.4` (new `$script:CommentsApiVersion`) because the Comments endpoints reject the plain `7.1` used elsewhere. New `Get-FieldValue` helper tolerates both PSCustomObject and the Dictionary fallback `Invoke-AdoRestMethod` returns for large payloads. Verified live against a Dataverse-backed Azure DevOps org: mention GUID resolved from `System.AssignedTo`, anchor markup correct, HTML entities round-tripped intact, test comment deleted after. |
